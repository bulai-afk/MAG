# Чат 02 — UI foundation и дизайн-система

Ты работаешь только над этапом 2 MAG. Прочитай `docs/PROJECT_PLAN.md`, особенно UX, дизайн-систему и раздел о графиках. Изучи результаты discovery и текущий frontend skeleton.

## Входное условие

Этап 1 завершён: monorepo запускается, проверки проходят, есть утверждённые CSV/KPI и структура отчёта.

## Цель

Совместно с владельцем продукта выбрать и утвердить стиль, структуру страниц и UI-компоненты, затем собрать полный happy path на реалистичных fixture-данных до подключения backend.

## Обязательный режим согласования

Не начинай полноценную вёрстку сразу. Работа разделена на дизайн-гейты. После каждого гейта покажи конкретный результат и запроси явное подтверждение владельца продукта.

Правила общения:

1. Задавай не более 1–2 связанных вопросов за сообщение.
2. Не спрашивай то, что уже определено в discovery-документах.
3. Для каждого существенного выбора предлагай 2–3 конкретных варианта.
4. Рекомендуемый вариант показывай первым и объясняй рекомендацию одним абзацем.
5. Не ограничивай вопрос словами «нравится / не нравится»: проси выбрать вариант или указать точное изменение.
6. После ответа фиксируй принятое решение.
7. Отделяй предпочтение владельца от требования пользователя и accessibility.
8. Не переходи к следующему гейту без явного «утверждаю» или эквивалентного подтверждения.
9. Если владелец просит изменить утверждённое решение, покажи влияние на уже выполненные экраны.
10. Все решения записывай в `docs/design/DESIGN_DECISIONS.md`.

## Гейт 1 — Визуальное направление

Сначала проведи короткое интервью о стиле:

- какие 3–5 качеств должен передавать продукт: надёжный, аналитичный, современный, спокойный, премиальный, дружелюбный;
- какие SaaS-интерфейсы нравятся и не нравятся владельцу и почему;
- светлая, тёмная или системная тема;
- строгий или более выразительный визуальный язык;
- компактная или просторная плотность;
- допустимая выразительность брендовых цветов;
- желаемая степень скругления;
- предпочтения по типографике;
- нужен ли собственный логотип на этапе MVP;
- какие визуальные приёмы недопустимы.

На основе ответов подготовь 2–3 style directions. Для каждого покажи:

- название и краткую идею;
- палитру ролей, а не только набор цветов;
- typography scale;
- spacing scale;
- border radius;
- стиль поверхностей и разделителей;
- кнопки, поля, карточку KPI, таблицу и пример графика;
- сильные стороны и риск для MAG;
- светлый desktop-фрагмент на одинаковом содержании для честного сравнения.

Не используй hardcoded цвета вне tokens, градиенты без продуктовой причины, декоративные тени на всех карточках и чрезмерное число accent colors.

**Результат гейта:** владелец выбирает одно направление и явно утверждает его.

## Гейт 2 — Информационная архитектура и страницы

До high-fidelity дизайна согласуй карту страниц и user flow:

- onboarding;
- вход и восстановление доступа;
- обзор;
- список клиентов;
- карточка клиента;
- список импортов;
- мастер импорта;
- список отчётов;
- редактор отчёта;
- preview;
- настройки бренда;
- настройки команды;
- использование и тариф;
- публичный клиентский отчёт;
- expired/revoked/PIN страницы.

Для каждой страницы зафиксируй:

- цель;
- основной пользователь;
- главное действие;
- обязательные данные;
- вторичные действия;
- навигацию;
- empty/loading/error/permission states;
- desktop и mobile приоритеты.

Покажи low-fidelity wireframes ключевого happy path. Для спорных экранов предложи альтернативы компоновки, например:

- sidebar против top navigation;
- список клиентов против карточек;
- пошаговый import wizard против единого экрана;
- редактор отчёта с правой preview-панелью против переключения режимов.

**Результат гейта:** утверждены карта страниц, навигация и wireframes.

## Гейт 3 — Дизайн-система и элементы

Создай отдельную демонстрационную страницу design system и согласуй элементы группами.

### Foundations

- semantic colors;
- typography;
- spacing;
- radius;
- borders;
- elevation, только где необходима;
- icon style;
- focus ring;
- breakpoints;
- motion и reduced motion.

### Controls

- primary/secondary/ghost/destructive buttons;
- text field;
- textarea;
- select;
- combobox;
- checkbox;
- radio;
- switch;
- date range;
- file dropzone;
- pagination.

### Feedback

- toast;
- inline validation;
- alert;
- progress;
- skeleton;
- empty state;
- error state;
- confirmation dialog.

### Product components

- AppShell и Sidebar;
- PageHeader;
- ClientCard/ClientRow;
- MetricCard;
- DeltaBadge;
- CsvPreview;
- ColumnMapper;
- ImportProgress;
- ChartCard;
- chart legend и tooltip;
- data table;
- NarrativeEditor;
- ReportSection;
- BrandPreview;
- PublishDialog;
- ShareLinkPanel;
- UsageMeter.

Для каждого компонента покажи нормальное, hover, focus, disabled, loading, error и mobile состояния, если применимо.

**Результат гейта:** foundations и компоненты утверждены до массового использования на страницах.

## Гейт 4 — High-fidelity ключевых экранов

Создай на fixture data и согласуй по одному:

1. AppShell и обзор.
2. Список и карточку клиента.
3. Мастер импорта и mapping.
4. Редактор отчёта.
5. Графики и таблицы.
6. Публичный отчёт.
7. Print/PDF.

Для каждого экрана:

- запусти приложение;
- открой экран в браузере;
- проверь desktop и mobile;
- покажи screenshot владельцу;
- назови принятые решения и оставшиеся вопросы;
- внеси согласованные изменения;
- запроси явное утверждение экрана.

Не переходи к следующему экрану с неразрешёнными замечаниями, влияющими на общую систему.

**Результат гейта:** ключевые high-fidelity экраны утверждены.

## Гейт 5 — Полная реализация UI

Только после утверждения гейтов 1–4:

1. Настрой Tailwind и shadcn/ui без дублирования дизайн-токенов.
2. Реализуй утверждённые AppShell, навигацию и layout-компоненты.
3. Сверстай все утверждённые страницы и состояния.
4. Создай KPI cards и графики MVP на fixture datasets.
5. Добавь table fallback для каждого графика.
6. Сделай адаптивный публичный отчёт.
7. Настрой print stylesheet и макет PDF.
8. Проверь keyboard navigation, contrast и reduced motion.
9. Добавь component, accessibility и visual regression tests.
10. Проведи финальный walkthrough happy path с владельцем.

## Артефакты этапа

Создай и поддерживай:

- `docs/design/DESIGN_BRIEF.md` — аудитория, характер и ограничения;
- `docs/design/DESIGN_DECISIONS.md` — журнал согласованных решений;
- `docs/design/INFORMATION_ARCHITECTURE.md` — страницы и навигация;
- `docs/design/USER_FLOWS.md` — ключевые сценарии;
- `docs/design/COMPONENT_INVENTORY.md` — компоненты и состояния;
- `docs/design/ACCESSIBILITY.md` — требования и результаты проверок;
- route `/design-system` или Storybook только если его стоимость оправдана текущим setup;
- visual fixtures для desktop, mobile и print.

Каждая запись в журнале решений должна содержать:

- вопрос;
- рассмотренные варианты;
- выбранный вариант;
- причину;
- дату и статус;
- экраны/компоненты, которых решение касается;
- условие возможного пересмотра.

## Ограничения

- Используй fixture data; не создавай временный псевдо-backend, который придётся поддерживать.
- Не реализуй auth, БД, CSV processing или AI.
- Не вводи свободный drag-and-drop конструктор.
- Текущий и предыдущий периоды должны визуально различаться не только цветом.
- Не подменяй согласование текстовым описанием: для визуального решения покажи визуальный результат.
- Не применяй выбранный стиль ко всему приложению до утверждения style direction.
- Не считай отсутствие ответа согласием.
- Не меняй shadcn-компоненты хаотично на уровне отдельных страниц; вариации должны идти через дизайн-систему.

## Готово, когда

- владелец явно утвердил style direction;
- карта страниц, навигация и wireframes согласованы;
- foundations и ключевые компоненты согласованы;
- каждый high-fidelity экран прошёл отдельный review;
- решения записаны в `DESIGN_DECISIONS.md`;
- happy path проходим без backend;
- интерфейс покрывает критические состояния;
- графики работают на desktop/mobile и имеют таблицы;
- print preview совпадает со структурой веб-отчёта;
- accessibility и visual tests проходят;
- финальный walkthrough утверждён владельцем.

В финале приложи список утверждённых решений, маршрутов, компонентов и состояний, screenshots ключевых экранов, результаты accessibility/visual tests и оставшиеся вопросы. Не объявляй этап завершённым без финального подтверждения владельца.
